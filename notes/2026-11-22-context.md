## 要点（Claude のまとめ）
### B. 考え方（コンテキストエンジニアリングとは）
- **AI に見せる情報の全体を、整理して保つこと。** プロンプト（頼み方）の次の段階。
  "curating and maintaining the optimal set of tokens"
- **見せる量には限りがあり、増えるほど効きが落ちる**（"context rot"）。
  "a finite resource with diminishing marginal returns"
- 目指すのは「**最小で、効き目の強い情報**」。"the smallest set of high-signal tokens"
- 指示は**ちょうどよい高さ**で書く。細かすぎる if-else の塊も、ぼんやりした指示も失敗する。最小でも、短いとは限らない
- ルールを並べるより、**代表的な例**を選ぶ。道具（ツール）も少なく、役割がはっきりしたものに絞る
- **全部を最初に入れず、場所だけ持たせて、必要なときに取りにいかせる**（just-in-time）。
  Claude Code は両方を使う。CLAUDE.md は最初に全部入れ、コードは grep などで都度探す
- 長い作業の 3 つの工夫
  - 圧縮: 会話を要約して続ける。大事な決定と未解決のバグは残す
  - メモ: 外部のファイルに書き、あとで読み戻す（to-do リスト、NOTES.md）
  - サブエージェント: 細かい作業を別に任せ、要約だけ返させる
- 結論: "do the simplest thing that works"（まず単純なことから）

### A. やり方（Claude Code での設定と運用）
- **指示には 2 種類ある。**
  - AI が読んで判断するもの（プロンプト、CLAUDE.md、skills）
  - 仕組みが必ず実行するもの（hook、deny ルール）
  - 例外を許さないルールは、後者にする
- **CLAUDE.md には「リポジトリを読んでも分からないこと」だけを書く。** "Only write down what Claude can't find by reading the repo"
  - 書くもの: 確認に使うコマンド、コードが誤解させる箇所、リポジトリの外で決めたこと、2 回以上直したこと
  - 書かないもの: コードを読めば分かること（構成の説明など）
  - **短く保つ**（200 行未満が目安）。1 行ごとに、関係のない作業でも AI の注意を少しずつ使う。
    "every line in it takes a little of Claude's attention on every task"
  - IMPORTANT などで強調しても守られないなら、長すぎるか、hook にすべきルール
- **必要なときだけ読ませる。**
  - 一部のフォルダだけのルールは `.claude/rules/` に置く
  - チームの手順は skills に置く（説明文だけ常に見えて、必要なときに全文を読む）
- **先に仕様を書かせる。** AI に質問させて SPEC.md を書かせ、実装は新しいセッションで。レビューも SPEC.md と比べる
- **合否が出る確認手段を渡す**（テスト、ビルド、リンター、スクリーンショット）。
  「全部通った」の一言でなく、実行したコマンドと出力を証拠として求める
- **会話が長いと、毎回全部を送る。** 関係のない作業の間は `/clear`、長いときは `/compact`。
  同じ直しが 2 回失敗したら、3 回目を頼まず `/clear` して頼み方を書き直す

### 2 つを並べると
| | B（考え方） | A（やり方） |
|---|---|---|
| いつも読ませる | CLAUDE.md は最初に全部入る、とだけ | 短く、リポジトリで分からないことだけ |
| 必要なときだけ | 段階的に見つけさせる（progressive disclosure） | rules・skills・サブエージェント |
| 探させる | just-in-time を詳しく説明 | 用語としては出てこない |
| 長い作業 | 圧縮・メモ・サブエージェント | `/clear`・`/compact`・新しいセッション |
| 仕様を先に | 記載なし | SPEC.md を書かせる |
| 確認 | 記載なし | 合否の出る手段と、証拠を求める |

## 01 の体験とのつながり（Claude の補足）
- **01 でやっていたことは、A がすすめる形そのものだった。**
  - lab ごとに新しいセッションで始めた（ほかの lab の文書を入れないため）
  - Spec Kit は仕様を先に書き、テストという合否の出る確認を持っていた
- **Spec Kit の constitution と skills は、「いつも読ませる」と「必要なときだけ」の分け方の実例。**
  constitution は毎回読む原則、`/speckit-*` は呼んだときだけ全文を読む
- **lab2 の Esc の穴**は、A の「確認手段を渡す」で言えば、手での確認（画面で試す）を渡していなかったところに当たる
- **01 の問い（複数のプロジェクトをまたぐ）** には、B の just-in-time が近い。
  全部の spec を読ませず、「どこに何があるか」の一覧だけを持たせ、必要な spec をその都度取りにいかせる

## 感想（自分の言葉で）
- **Spec Kit などの SDD は、A の実践に見える。プロジェクトの背景などを渡すのがコンテキストエンジニアリングなら、
  SDD はその子のコンテキストエンジニアリングとして理解してよいか**
  - 補足: AI に渡す面では、そのとおり。SDD は「何を作るか」を、どの形で、どの順で渡すかを決めた型
    | B の考え方 | SDD（Spec Kit）での形 |
    |---|---|
    | いつも読ませる | constitution（原則） |
    | 必要なときだけ読ませる | 段ごとの文書（spec は plan の、plan は tasks の入力） |
    | 場所だけ持たせて取りにいかせる | tasks に `FR-012` などの番号を書き、必要な仕様を引かせる |
    | 外部のメモで長い作業を続ける | tasks.md のチェックボックス |
    | 新しいセッションで始める | 段ごとに文書へ書き出すので、会話の履歴に頼らない |
    - プロジェクトの背景は「いつも読ませる層」、変更ごとの spec は「必要なときに読ませる層」として並べられる
  - 補足: ただし SDD には、コンテキストエンジニアリングに収まらない面もある。「子」より「大部分が重なる」が正確
    - 人どうしの合意の文書でもある（PM や関係者がレビューして「これで作る」と決める。AI がいなくても意味がある）
    - 確かめる仕組みを持つ（analyze・converge・テスト先行）。「何を見せるか」ではなく「結果が正しいか」の話で、05 Evals・04 ハーネスに近い
    - 正本として残り続ける（コンテキストは 1 回の作業のため。spec はシステムのいまの振る舞いの記録。lab4 の OpenSpec）
