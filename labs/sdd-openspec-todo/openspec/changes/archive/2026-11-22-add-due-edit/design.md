# Design

## Context

- 編集はいま、行を文言の入力欄と「確定」「取り消し」のフォームに差し替える形で作られている。編集の状態は `{ id, draft }`（`draft` は書きかけの文言）で、保存しない
- 編集中の行には「期限: 〜」と「期限切れ」の印をそのまま出している
- 追加のフォームの期限は `<input type="date">` で、空文字なら期限なし（`null`）として保存している
- 保存データの期限は `null` か `YYYY-MM-DD` で、読み込むときにこの形を確かめている

## Goals / Non-Goals

**Goals:**
- いまの編集の流れ（始める・確定・取り消し・1 行だけ・Esc・行の外のクリック）を変えずに、期限の日付欄を 1 つ足す
- 文言の編集に関する既存のテストを、できるだけそのまま通す

**Non-Goals:**
- 期限だけの編集ボタン、日付の入力部品の自作、日付の範囲（過去日の禁止など）の制限
- 保存の形式や保存キーの変更

## Decisions

### 1. 編集の状態に書きかけの期限を足す
`state.editing` を `{ id, draft, dueDraft }` にする。`dueDraft` は日付欄の値（`YYYY-MM-DD` か空文字）。
文言が決まりに合わずに描き直すときも、`dueDraft` を残して日付欄に戻す。
- 代案: 描き直さずに DOM の値をそのまま残す → いまの作りは状態から描き直す形なので、合わせる

### 2. 期限を変える純粋関数を別に足す
`todo.js` に `editDue(todos, id, due)`（空文字は `null`）を足し、確定では `editTodo` のあとに `editDue` を当てる。
- 代案: `editTodo` の引数を `{ title, due }` に変える → 既存の単体テスト（`editTodo` は期限を変えない）を書き直すことになる。関数を分ければ既存テストはそのまま通り、「文言の決まり」と「期限」の責任も分かれる

### 3. 編集中の行では「期限: 〜」の文字を日付欄に置き換え、「期限切れ」の印は残す
期限の文字と日付欄が並ぶと同じ情報が 2 つになるので、文字は出さない。「期限切れ」は確定前の（保存されている）期限で判断して出し続ける。
- 日付欄の読み上げ名は「期限」。文言の入力欄（「やることの文言」）の次に置く

### 4. 日付欄の値の扱いは、追加のフォームと同じにする
日付欄の `value` が空文字なら期限なしにする。ブラウザの日付欄は、書きかけの不完全な日付も `value` を空文字にするので、その場合も期限なしとして確定される。
- 代案: 不完全な日付（`validity.badInput`）では確定しない → 追加のフォームにもない決まりで、依頼の範囲を超える。Risks に書き、必要なら別の変更にする

### 5. Esc と Enter はいまの仕組みのまま日付欄にも効かせる
Esc は一覧の `keydown` で、Enter はフォームの送信で受けているので、日付欄をフォームに入れるだけで効く。新しいイベントの処理は足さない。

### 6. capability の名前は `todo-title-edit` のまま残す
差分では capability の名前を変えられないので、要件の名前だけを RENAMED で「文言の編集〜」から「編集〜」に変えた。capability の名前と Purpose（「文言を…」）は中身とずれたまま残る。
- Purpose は archive のあとに正本を直接直す（tasks の Workflow follow-up に書く）
- capability の名前（例: `todo-edit`）の変更は、必要なら別の変更として行う

## Risks / Trade-offs

- [日付欄に書きかけの日付があると、確定で期限が消える] → 追加のフォームと同じふるまいなので受け入れる。困るなら別の変更で「不完全な日付では確定しない」を検討する
- [既存の UI テストのうち、編集中の行の「期限: 〜」の文字を前提にしたもの（行の中のクリックで取り消さない）が通らなくなる] → spec のシナリオも「日付欄」に書き換えたので、テストもそれに合わせて書き直す。書き直したテストは tasks に明記する
- [capability の名前と中身がずれる] → Decision 6 のとおり、記録して別の変更に回す
