# 01 SDD（Spec-Driven Development, 仕様駆動開発）
<!-- Last updated: 2026-11-22 -->

## 一言で
コードより先に「仕様」を正として書き、AI はその仕様から計画・タスク・実装を作る。
「雰囲気でプロンプトして書かせる（vibe coding）」の反対側。

## 学ぶこと
1. 考え方: なぜ仕様を正にするのか（意図の固定・レビュー単位・再生成できること）
2. 成果物の型: 原則（constitution）→ 仕様（spec / requirements）→ 設計（plan / design）→ タスク（tasks）→ 実装
3. 要件の書き方: ユーザーストーリー、受け入れ条件、EARS 記法（「〜のとき、システムは〜しなければならない」）
4. ツール比較: GitHub Spec Kit／Kiro／Claude Code だけで回す方法
5. 限界: 仕様と実装のずれ、仕様の書きすぎ、変更時の運用

## まとめ: 業務システムの改修に SDD を持ち込むなら（2026-11-22、一般論）
自分の考え（太字）に、lab1〜3 の体験からの補足を足した。立場は **PM 側**（コードは書かず、広い範囲で仕様を理解し、レビューと確認をする）。
lab はコードまで作る開発者の目線だったので、そのまま当てはまらないところもある。

### 1. 何を仕様にするか
- **現状あるものをベースに、既存を整理する。これからの改修分は lab3 の形で足していく**
  - 補足: 既存の整理は一度に全部でなくてよい。改修で触る範囲とその周りから始める。
    既存の振る舞いは、今あるコードや画面の操作から AI に下書きさせ、人が確かめる形が現実的
  - 補足: 改修分は「1 つの変更 = 1 つの仕様」として足す（lab3 の Spec Kit は `002` として追加し、001 には「002 で範囲内にした」と追記した）。
    古い記述（「やらないこと」など）が残らないかを毎回確かめる
- **技術選定は仕様書に書かない**（計画・設計の側に書く）
- 補足: 仕様に書くのは「何を・なぜ」に加えて、範囲（やらないこと）、確かめられる受け入れ条件、前提と誰が決めたか、境界のケース

### 2. 人が関わるところ
- **仕様書の段階で AI と一緒に作る → できた文書をレビューする → 最後に出来上がったもののデザインと挙動を確かめる**
  - 補足: 仕様書の段では、AI の質問に答える（clarify）、別の目でレビューさせる（lab2 の 1.5 で 32 件の穴）。
    AI が「おまかせ」で決めたところに印を残すと、PM がどこを確かめればよいかが分かる
  - 補足: 最後の挙動の確認は省けない。lab3 では、自動テストが全部通っていても、日本語入力の変換中の Esc で編集が消える穴が残った
  - 補足: 計画やタスク（plan・tasks）は開発側の文書。PM が細かく読むより、仕様（受け入れ条件）との対応が取れているかを見る
- **機能ごとの spec を全部読むのは大変**（lab4 の OpenSpec: 5 ファイル・443 行、要件 26・シナリオ 65。シナリオが大半）
  - 補足: PM は**要件の見出しだけ**を読んで、抜けや余計なものがないかを見る（26 行で全体が見渡せた）。気になった要件だけ本文とシナリオを読む
  - 補足: シナリオ（WHEN / THEN の例）は開発とテストのためのもの。読みやすさのために削ると、境界のケースが抜けやすくなるので厚く残す
  - 補足: 見出しの一覧は道具でも出せる（OpenSpec なら `openspec view`、`openspec show <spec> --json --no-scenarios`。2026-11-22 確認）

### 3. PM から見た SDD の価値
- 補足: 仕様が「正」として残り続けるので、広い範囲の振る舞いを文書で把握できる（設計書のように古くなりにくい。ただし確かめる段があれば）
- 補足: 受け入れ条件がそのまま確認の観点になる（lab では受け入れ条件 1 つ = テスト 1 つで対応が追えた）
- 補足: 進め方の選び方。確かめる段が多い Spec Kit 型は、大きい改修・要件があいまいなものに向く。
  シンプルな Kiro 型は小さい改修向きだが、書き手の表現力で質が決まり、手戻りが起きやすい

### まだ分からないこと（01 の範囲を超える問い）
- **複数の PJ をまたいでいるので、機能ごとの spec だけでは足りない**
  - 補足: 機能ごとの spec は一番下の層。その上に、次の層がほしい
    - プロジェクトをまたぐ全体図（どのシステムが、どの機能を持っているか）
    - **システムどうしのつながり**（データの受け渡し・連携の約束）。どのプロジェクトの spec にも載らず、すき間に落ちやすい。
      改修の影響がプロジェクトの外に及ぶのは、たいていここから
    - 変更の流れ（最近どのプロジェクトで何が、なぜ変わったか）
    - 1 プロジェクトの概要（要件の見出しを抜き出せば作れる）
  - 補足: 試したい案
    - spec の決まった形（要件の見出し、proposal の Why / What Changes）から、AI やスクリプトでプロジェクトをまたいだ一覧や変更のまとめを作る
    - システムの間の約束は、どちらか一方ではなく、共通の場所に spec として置く
    - OpenSpec の「store」（ベータ版。独立した OpenSpec のリポジトリをマシンに登録する仕組み）が使えるか。**ドキュメントは未読（要確認）**
  - 補足: つながるテーマ: 02 コンテキストエンジニアリング（AI にどの情報をどの層で渡すか）、06 RAG とメモリ（たくさんの文書から必要なところを探す）

## 理解度チェック（自分の言葉で答えられたら ✅）
答えは 2026-11-22 に自分の言葉で答え、Claude の補足を足したもの。太字が自分の答え。

- [x] SDD と TDD・従来の設計書駆動の違い
  - **TDD はエンジニアが関数ごとに実装し、ユニットの正しさを確かめるため。SDD のテストはもっと範囲が広く、AI に仕様を渡して仕様どおりになっているかを確かめる（BDD に近い）**
  - **設計書は書いたら古くなるが、SDD は仕様を先に直して AI に追従させる**
  - 補足: SDD と TDD は組み合わせられる（lab1 は SDD の中でタスクごとに TDD）。追従は確かめないと崩れる（analyze・converge。lab2 は確かめる段がなく、ずれが実装中まで残った）
- [x] 仕様に書くこと／書かないこと
  - **仕様には「何を」「なぜ」を書き、技術や作り方は書かない**（lab2 で「DOM Storage」→「閉じても消えない」に直した）
  - 補足: 「何を」には、範囲（やらないこと）、確かめられる受け入れ条件、前提と誰が決めたか、境界のケース（空・失敗・同時の操作）まで含める
- [x] 仕様と実装がずれたとき、どちらを直すか
  - **仕様を先に直して、実装を追従させる**
  - 補足: 仕様がいつも正しいとは限らない。まずどちらの振る舞いが正しいかを決め、その結果を先に仕様に書く（lab2 の 6.5 は実装が正しく、仕様を直して終わった）
