# 02 コンテキストエンジニアリング
<!-- Last updated: 2026-11-22 -->

## 一言で
AI の出来は「何を頼むか（プロンプト）」より「**何を、いつ、どれだけ見せるか**（コンテキスト）」で決まる。
渡す情報を設計する。多すぎても少なすぎても、AI は間違える。

## 01 からつながる問い
- 01 の最後に残した問い: **複数の PJ をまたいでいるので、機能ごとの spec だけでは足りない**（[01 のまとめ](../01-sdd/README.md)）
- 01 の lab で、すでにコンテキストを設計していた。たとえば次のもの
  - Spec Kit の constitution（毎回守る原則）
  - Kiro の steering（いつも読ませる背景）
  - OpenSpec の `config.yaml` の `context`（成果物は日本語で、コメントの FR 番号は以前の仕様の名残）
  - lab ごとに新しいセッションで始めたこと（ほかの lab の文書を文脈に入れないため）
- 02 では、これを「なんとなく」から「設計」にする

## 学ぶこと
1. 考え方: AI が一度に見られる量には限りがあり、量が増えると注意が薄まる。必要な情報を、必要なときに、最小限で渡す
2. 層に分ける
   - いつも読ませるもの（CLAUDE.md・原則）
   - 必要なときだけ読ませるもの（スキル・特定のフォルダだけのルール・spec）
   - その都度、探させるもの（コード・文書の検索）
3. CLAUDE.md の書き方
   - 何を書き、何を書かないか（コードを読めば分かることは書かない）
   - 長さ
   - 必ず守らせたいことは、文書ではなく仕組み（hook など）に移す
4. 長い作業での工夫: 外部のメモに進み具合を書き、あとで読み戻す。セッションを分ける（仕様を書くセッションと、実装するセッション）
5. PM の目線: たくさんのプロジェクトと文書の中から、AI に何を常に見せ、何を探させるか

## 課題
- [ ] 読む: 教材の 2 つを読み、要点と感想を `notes/` に残す（要点は Claude にまとめさせ、感想は自分の言葉で）
- [ ] lab5: CLAUDE.md の良し悪しを比べる（`labs/context-claude-md/`、これから作る）
  - 同じ TODO アプリ（lab1 か lab4 のコピー）に、CLAUDE.md を 3 通り用意する
    - なし
    - 長い（思いつくことを全部書く）
    - 短い（教材の基準で、要点だけ）
  - 同じ依頼を、それぞれ新しいセッションで渡し、結果を比べる。比べる観点の案
    - 依頼どおりか
    - 決まりを守ったか（テスト先行・依存を増やさない など）
    - 見落としがあったか（01 の Esc の穴のような）
    - 確認の回数と手間
- [ ] まとめ: 複数のプロジェクトをまたぐとき、AI に渡す情報をどう層に分けるかを、一般論で書く（01 の問いへの答え）
