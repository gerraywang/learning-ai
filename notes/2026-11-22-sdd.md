## 分かったこと
- **成果物が「次の段の入力」になっている。** spec は plan の、plan は tasks の、tasks は implement の入力。
  前の段を直さずに後ろだけ直すと、次に流したときに元に戻る。だから「文書を先に直す」（原則 IV）が効く
- **spec に「どう作るか」を書かないのは、決めないことではない。** 「端末内に保存」は spec では
  「再起動しても残る」「外へ送らない」という振る舞い（FR-012 / FR-013）として書き、localStorage は plan で決めた
- **説明文が短いと、AI が前提を決める。** 200 文字の上限・削除は確認なし・編集は範囲外 などは
  spec の Assumptions に AI が書いたもの。clarify を飛ばしたので、人が選ぶ機会がなかった
- **analyze は「原則どうしの食い違い」も見つける。** 原則 IV（各タスクは要求を参照）が Setup タスクと合わず
  CRITICAL になった。直し方は「タスクを直す」か「原則を改定する」かの 2 択で、後者（v1.1.0）を選んだ
- **contracts（画面の約束）がテストの探し方を決める。** ラベル・文言・`data-id` を contracts に書いたので、
  テストがそれで要素を探せた。「同じ文言の行を区別できない」は analyze の段で見つかり、実装前に直せた
- **テスト先行は「失敗の理由」まで見ないと形だけになる。** 1 回、失敗の原因が機能の欠如ではなく
  テストのヘルパーのバグだった。また「〜にならない」型のテストは実装前から通ってしまう
- **converge は「機能の作り残し」だけでなく原則違反も拾う。** 1 回目は機能は全部あったが、
  未使用の戻り値（原則 III）など 3 件を追加タスクにした。直して 2 回目で Converged
