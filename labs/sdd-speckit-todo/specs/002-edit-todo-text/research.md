# Research: やることの文言を後から編集する

**Date**: 2026-11-22 | **Plan**: [plan.md](./plan.md) | **Spec**: [spec.md](./spec.md)

技術（Vite・素の JavaScript・localStorage・Vitest + jsdom）は 001 と同じ
（[001 research.md](../001-todo-app/research.md) R1〜R7）。ここでは本機能で新しく決めることだけを書く。
外部の情報は使っていない（ブラウザの標準の振る舞いだけに依る）。

## R1. 編集の始め方: 各行に「編集」ボタン

- **決定**: 各行の削除ボタンの前に「編集」ボタンを置く。読み上げ用の名前は「<文言> を編集」。
- **理由**: キーボードだけでも届き（Tab で移動して Enter）、テストでも「どの行のボタンか」を
  名前で探せる。削除ボタンと同じ作りなので概念が増えない（原則 III）。
- **ほかの案**: 文言のダブルクリックで編集 → キーボードで始められず、完了チェックのラベル
  （文言をクリックすると完了が切り替わる）とぶつかる。文言を常に入力欄にしておく → 「確定」
  「取り消し」の区切りがなくなり、spec の US2 を満たしにくい。

## R2. 編集中の行の作り: 行の中に小さなフォーム

- **決定**: 編集中の行は、完了チェック・文言・編集・削除の代わりに、`<form>` の中に
  文言の入力欄（読み上げ名「やることの文言」）・「確定」ボタン（submit）・「取り消し」ボタンを出す。
  期限と期限切れの印はそのまま表示する。
- **理由**: `<form>` にすると、入力欄で Enter を押したときの確定（FR-012）をブラウザの標準の
  送信で受けられ、追加フォームと同じ作りになる。日本語入力の変換を Enter で決めたときは、
  ブラウザは送信しないので、追加と同じく別の対策は要らない。
- **ほかの案**: 入力欄の keydown で Enter を自分で拾う → 変換中の Enter（`isComposing`）を
  自分で除く必要があり、コードが増える。

## R3. 取り消しのキー: 入力欄の keydown で Escape

- **決定**: 編集の入力欄で `keydown` の `key === 'Escape'` を受けたら取り消す。ただし
  `event.isComposing` が true のとき（日本語の変換中）は何もしない。
- **理由**: 変換中の Esc は「変換をやめる」操作で、編集の取り消しと取り違えると書きかけが消える。

## R4. 「編集中の行の外のクリック」での取り消し: document の click で、編集中の行だけを描き直す

- **決定**: `document` で `click` を受け、編集中で、クリックした要素が画面につながっていて
  （`isConnected`）、編集中の行の外なら取り消す。取り消すときは **編集中の行だけ** を通常の行に
  描き直す（一覧全体は描き直さない）。
- **理由**:
  - 一覧の中の操作（別の行の完了チェック・削除・編集開始）と絞り込みは、それぞれの処理の中で
    編集を終わらせる（FR-004）。document の click はそれより後に届くので、何もしなくてよい。
  - 完了チェックは、click の後に change が届く。ここで一覧全体を描き直すとチェックボックスが
    画面から外れて change が一覧に届かない。編集中の行だけを描き直せば、ほかの行の部品は残る。
  - 別の行の「編集」を押したときは、先に一覧の処理で描き直されて押したボタンが画面から外れる。
    `isConnected` で見分けて、新しい編集を取り消さないようにする。
- **ほかの案**: 入力欄の `blur`（フォーカスが外れたら取り消し）→ Safari などではボタンを押しても
  フォーカスが移らないことがあり、「確定」を押した瞬間に取り消されるおそれがある。
- **範囲**: Tab キーでフォーカスを外へ移すだけでは取り消さない（spec は「クリック」の場合を
  決めている。キー操作の利用者は Esc で取り消せる）。

## R5. 編集中の状態の持ち方: `state.editing = { id, draft } | null`

- **決定**: 画面の状態に、編集中のやることの `id` と、書きかけの文言 `draft` を持つ。`draft` は
  編集を始めたときは今の文言、決まりに合わず確定できなかったときは入力した文言にする。保存しない。
- **理由**: 確定できなかったとき（FR-006）もお知らせを出すために描き直すので、入力した文言を
  覚えておく場所が要る。入力のたびに覚える必要はない（ほかの描き直しは編集を終わらせるため）。

## R6. 文言の変更: `todo.js` に純粋関数 `editTodo` を足す

- **決定**: `editTodo(todos, id, title)` は、指定した id の `title` だけを変えた新しい配列を返す。
  検証は追加と同じ `validateTitle` を通してから呼ぶ（FR-006）。
- **理由**: 001 の `toggleTodo` / `removeTodo` と同じ形にそろえる。期限・完了・順番を変えないこと
  （FR-007）を単体テストで確かめやすい。
- 保存形式（contracts/storage.md）は変わらない。保存は既存の「操作のあとに全体を保存する」
  処理をそのまま使う（FR-008 / FR-011）。

## R7. 確定・取り消しの後のフォーカス

- **決定**: 確定（成功）と取り消しの後は、その行の「編集」ボタンにフォーカスを戻す。外の
  クリックで取り消したときは戻さない（クリックした先にフォーカスがあるため）。
- **理由**: キーボードで操作している人が、描き直しで位置を見失わないようにする（最低限の配慮。
  001 R7 と同じ考え）。

## R8. 既存テストのヘルパーの手直し

- **決定**: `tests/helpers/render-app.js` の `deleteButton` は、行の中の「最初のボタン」ではなく
  `button.remove` で探すように直す。
- **理由**: 行に「編集」ボタンが増えるため、最初のボタンが削除ボタンでなくなる。テストの中身
  （001 の受け入れシナリオ）は変えない。
