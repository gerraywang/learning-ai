## 分かったこと
- **成果物が「次の段の入力」になっている。** spec は plan の、plan は tasks の、tasks は implement の入力。
  前の段を直さずに後ろだけ直すと、次に流したときに元に戻る。だから「文書を先に直す」（原則 IV）が効く
- **spec に「どう作るか」を書かないのは、決めないことではない。** 「端末内に保存」は spec では
  「再起動しても残る」「外へ送らない」という振る舞い（FR-012 / FR-013）として書き、localStorage は plan で決めた
- **説明文が短いと、AI が前提を決める。** 200 文字の上限・削除は確認なし・編集は範囲外 などは
  spec の Assumptions に AI が書いたもの。clarify を飛ばしたので、人が選ぶ機会がなかった
- **analyze は「原則どうしの食い違い」も見つける。** 原則 IV（各タスクは要求を参照）が Setup タスクと合わず
  CRITICAL になった。直し方は「タスクを直す」か「原則を改定する」かの 2 択で、後者（v1.1.0）を選んだ
- **contracts（画面の約束）がテストの探し方を決める。** ラベル・文言・`data-id` を contracts に書いたので、
  テストがそれで要素を探せた。「同じ文言の行を区別できない」は analyze の段で見つかり、実装前に直せた
- **テスト先行は「失敗の理由」まで見ないと形だけになる。** 1 回、失敗の原因が機能の欠如ではなく
  テストのヘルパーのバグだった。また「〜にならない」型のテストは実装前から通ってしまう
- **converge は「機能の作り残し」だけでなく原則違反も拾う。** 1 回目は機能は全部あったが、
  未使用の戻り値（原則 III）など 3 件を追加タスクにした。直して 2 回目で Converged

### Spec Kit と Kiro の違い（lab2 の途中で、2026-11-22）
- **ひとことで: Spec Kit は「ユースケース → 機能」、Kiro（今回の lab2）は「機能群」で作業を切る。**
- Spec Kit はユーザーストーリーに優先度（P1〜P5）を付け、tasks もストーリーごとのフェーズに切る。
  テンプレートが「各ストーリーは単独でテスト・デモできること」を求めていて、US1 だけで動く MVP になる
- lab2 の tasks は機能のまとまり（保存・追加・期限切れ・完了・削除・絞り込み）で切った。
  **ただし、そう切ったのは今回の自分たちの選択。** Kiro のドキュメントには tasks の切り方・書式の記載がない。
  言えるのは「Kiro は tasks の切り方を決めていない」まで
- 要件の段では両方ともユーザーストーリーから入る（Kiro の requirements.md も要件ごとにストーリーと受け入れ条件を持つ）。
  違いは、ストーリーを「作って届ける単位」にまでするか（Spec Kit）、要件の整理に使うだけか（Kiro）
- 予想: lab1 は US1 が終わった時点で画面で試せた。lab2 はグループ 4（追加）まで終わらないと何も試せない。
  実装（段 4）で確かめる

### AI で作るなら、途中結果を見る価値はあるか（2026-11-22）
- 疑問: AI が数分で全部作るなら、ストーリーごとに途中結果を見る（MVP で切る）価値は小さいのでは
- 考え: **価値はなくならず、中身が「早く届ける」から「早く確かめる・少しずつ直す」に移る**
  - 薄れる価値: 作るのに時間がかかる前提での「途中でも早く届ける」「遅れても P1 だけは出す」
  - 残る（増える）価値:
    1. 詰まるのは書く速さではなく、人が読んで確かめる量。区切れば 1 回に確かめる量が小さい
    2. 思い違いを早く見つけられる（lab1 では US1 の段階でテストのヘルパーのバグに気づけた）
    3. 動くものを見ると要件が変わる（「みせて」→「やっぱりこうしたい」）。早いほど作り直しが小さい
    4. AI の長い作業に区切りができ、文書からのずれを止め、戻る地点（コミット）を作れる
  - 小さなアプリでは薄く、大きいもの・要件があいまいなものほど効く
- lab2 で確かめること: 実装は「上から順に全部」で頼み、終わったあとに
  **確かめるのにかかった手間**と、**画面を見てから直したくなったこと**を記録して lab1 と比べる

### Kiro でもユースケース単位で切れるか（2026-11-22）
- 考え: **切り方次第。** Kiro は tasks の切り方を決めていないので、ユースケース単位で切れば Spec Kit と同じ進め方ができる
  - lab2 の requirements は要件 1〜5 がそれぞれユーザーストーリー（ほぼユースケース）なので、要件ごとに tasks を切ればよい
- ただし Spec Kit がテンプレートとコマンドで支えていたものは、自分で補う必要がある
  | Spec Kit が支えていたもの | Kiro 風で補う方法 |
  |---|---|
  | ストーリーの優先度（P1〜P5） | requirements.md に優先度を書き、tasks もその順にする |
  | 「各ストーリーは単独でテスト・デモできる」という決まり | tasks.md の冒頭に約束として書く |
  | ストーリーの前に置く土台（Foundational） | 準備・保存・描画の骨組みを最初のグループにする |
  | 横断する要件（保存など）の扱い | 独立したグループにせず、各ストーリーのタスクに「保存されること」まで含める |
- Kiro 本体では、依存のないタスクをまとめて並行に進める（waves）。ユースケースごとに止めて確かめたいなら、1 つずつ実行する
- lab2 は機能のまとまりで切ったまま実装する（切り方の違いを確かめるため）。
  ユースケース単位の Kiro 版は lab3 の手前で試すと、差が「切り方」から来るのか「道具」から来るのかを分けて見られる

### テストファーストは Kiro にないのか（2026-11-22）
- **Kiro にはテストを先に書かせる仕組みはない。** ただし **Spec Kit にも最初からはない**
  - Kiro: Specs・Requirements-First・Correctness・Steering のページに test-first / TDD の記載なし
    （https://kiro.dev/docs/specs/ ほか、確認日 2026-11-22）
  - Spec Kit: tasks のテンプレートに「Tests are OPTIONAL - only include them if explicitly requested」。
    lab1 でテストが先に来たのは、constitution の原則 I（テスト先行）を自分たちで書いたから
- Kiro の代わりのもの: **Correctness（property-based testing）**
  - 設計の段で EARS の受け入れ条件から「常に成り立つべき性質」を取り出してテストを作り、タスク実行時にランダムな入力で何百〜何千通り試す
  - 既定は任意（オフ）。IDE のみ。「正しさの証拠であって証明ではない」とドキュメント自身が書いている
    （https://kiro.dev/docs/specs/correctness/ 、確認日 2026-11-22）
  - 「先にテストを書く」ではなく「要件から性質を検証する」という発想
- ルールを書く場所と、守らせる力の違い
  | | ルールを書く場所 | 守らせる仕組み |
  |---|---|---|
  | Spec Kit | constitution | plan の Constitution Check、analyze・converge が違反を CRITICAL として指摘 |
  | Kiro | steering（`.kiro/steering/*.md`、毎回の対話に読み込まれる） | 読み込まれるだけ。確かめるコマンドはない |
  | lab2（今回） | tasks.md の冒頭の約束 | 実装する AI が読んで守るか次第 |
- lab2 の実装で「テストを先に書き、失敗を確かめたか」を見て答え合わせする

### lab2 を実装・確認して分かったこと（2026-11-22）
- **予想どおり、グループ 4（追加）まで画面では何も試せなかった。** 1〜3 は準備・テストの土台・保存で、
  画面に出るものがない。しかも今回は一気に作らせたので、自分が画面を見たのは全部できたあと
- **EARS の受け入れ条件は、そのまま画面テストになった。** 1 条件＝1 テスト、テスト名の先頭に番号（`1.8: …`）。
  33 個そろっているかを grep で数えられる。FR-xxx と違い、条件（WHEN）と結果（SHALL）が分かれているのでテストの準備と確認に割りやすい
- **テストは先に書かれた。ただし守らせたのは tasks.md の順番だけ。** 各グループで「書く → 失敗 → 実装 → 通る」を踏んだが、
  それを確かめたのは実装した AI 自身。lab1 と同じ落とし穴も出た:
  - 失敗の理由が「機能がない」ではなく「モジュールがない」（テストが 0 件のまま失敗）だった回がある
  - テストのヘルパーのバグ（jsdom 環境では `import.meta.url` が `file:` にならない）がグループ 4 で見つかった
  - 「〜しない」型のテスト（3.2 未完了に戻す）は実装前から通った
- **文書どうしの食い違いは、実装の途中で初めて見つかった。** requirements 6.5「読み出し禁止 → 読み込めなかったと知らせる」と、
  design の「保存先が使えない」の文言。Spec Kit なら analyze で実装前に見つかった種類のもの。Kiro 風の手書きにはこの関所がない
- **文書に書いていないことを、AI は 6 点足した。** フォームの `novalidate`（ブラウザの `required` が先に止めると 1.8 の表示が出ない）、
  描き直したあとのフォーカスの戻し方（7.2 のため）など。どれも筋は通るが、「書いていないことは作らない」と頼んでも、
  動かすために必要なことは足される。足したものを最後に一覧で報告させると、前提の量を数えられる
- **画面の確認も AI に任せられるが、全部ではない。** Chrome の操作で 33 個のうち大半を確かめられた。
  残ったのは、ブラウザの設定を変える必要があるもの（起動時に保存先が使えない）、他のブラウザ（7.1）、キーボードだけの通し操作（7.2）。
  日付欄は自動のキー入力だと桁がずれ、値を JavaScript で入れる回り道をした
- 途中結果を見る価値について: 今回は大きな手戻りがなく、一気に作らせても困らなかった。小さなアプリでは差が出にくいという予想どおり。
  「画面を見てから直したくなったこと」は自分で記入してから判断する
